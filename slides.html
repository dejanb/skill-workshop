Three kinds of trigger prompts

tests:
  # Positive — should trigger
  - vars:
      prompt: 'Review this code for security vulnerabilities'
    assert:
      - type: skill-used
        value: security-review

  # Near-miss — should trigger sibling, not this one
  - vars:
      prompt: 'Check if the code follows our naming conventions'
    assert:
      - type: not-skill-used
        value: security-review
      - type: skill-used
        value: style-check

  # Negative — unrelated, should trigger nothing
  - vars:
      prompt: 'What time is the standup meeting?'
    assert:
      - type: not-skill-used
        value: security-review

Choose the execution environment and the grading method separately.

One agent run can have JSON, code, and model-graded assertions.

So far we checked whether a skill was selected and put that check in CI. Now broaden the assertions. The provider runs the system under test; an assertion grades evidence from that run. JSON is an output format. An agent is an execution environment. An LLM judge is a grading method. These choices can be combined in one eval.

Sources: Promptfoo assertions, Claude Agent SDK provider.

Exact checks

AssertionUseful for
equalsAn exact status or classification
contains / not-containsRequired or forbidden literal text
regex / not-regexA heading or other text pattern
 
# Check a heading, allowing the words elsewhere in the report
assert:
  - type: not-regex
    value: '(^|\n)### \*\*Root Cause\*\*(\r?\n|$)'

Make the check as precise as the rule it protects.

A skipped optional section gives us a concrete example. Forbidding the words Root Cause everywhere would also reject a valid note explaining what was skipped. This expression checks the actual Markdown heading. Exact checks are repeatable and require no judge-model call; choosing the right condition still takes judgment.

Source: Promptfoo deterministic assertions.

is-json: whole output. contains-json: JSON within other text.

The schema checks required fields and their types. It intentionally accepts any string in labels, so the wrong label can pass. A schema can also enforce an enum or const; the next slide uses code to show how domain rules can be expressed separately. A provider's structured-output setting constrains generation, while this assertion checks the returned result.

Source: Promptfoo JSON assertions and schemas.

JavaScript assertions

assert:
  - type: javascript
    value: |
      try {
        const report = typeof output === 'string'
          ? JSON.parse(output) : output;
        const pass = Array.isArray(report?.labels) &&
          report.labels.includes('ai-generated-jira');
        return { pass, score: pass ? 1 : 0,
          reason: pass ? 'Required label present'
                       : 'Required label missing' };
      } catch {
        return { pass: false, score: 0, reason: 'Invalid JSON' };
      }

Use code for exact fields, counts, and relationships.

Python assertions are also supported. Larger graders can live in file:// scripts.

The wrong label from the previous slide now fails. Parsing errors fail too, instead of becoming an empty result that accidentally passes. Returning a reason makes a failed assertion easier to investigate. Code can enforce a known contract, but this check alone says nothing about whether the report preserves the user's facts.

Execution testing

Does the agent carry out the task correctly?


Give it a defined situation.
Observe its behavior and check the result.

Trigger testing asks whether the agent selects a skill. Execution testing asks what happens when it uses the skill. The result might be an answer, a generated artifact, or a change in an external system. We first need a few concepts for setting up these tests.

Source: Anthropic, task definitions and outcomes in agent evals.

Scenarios

A repeatable situation we want to test


  • A task and the information available at the start
  • Conditions the agent encounters
  • Expected behavior or an acceptable result

Example: required information is missing. Should the agent ask for it?

A scenario is a test case: a task, its context, and criteria for success. We can create scenarios for a normal request, incomplete input, or a dependency failure. Repeating a scenario helps us compare behavior. The expected result belongs to the evaluation; giving the agent the answer would weaken the test.

Mocks

Controlled replacements for tools or services


  • Return a chosen response when the agent makes a call
  • Make success and failure conditions repeatable
  • Record calls so we can check how a dependency was used

Example: an API returns a timeout. How does the agent respond?

A test double stands in for a real dependency. A stub supplies a response; a mock can also check interactions. Here we use mocks as the broad introductory term for controlled tool or service replacements. The agent still chooses whether and how to call the tool. These tests tell us about its response to the simulated behavior; testing the real integration is a separate step.

Sandboxes

Isolated environments for running actions


  • Allow real tools to operate on test data
  • Enforce limits on what execution can access or change
  • Start each run from a known state

Example: create and edit files inside a disposable test environment.

The sandbox provides an execution boundary. Its configuration determines file, process, and network access. Resetting test state supports repeatability; isolation controls side effects. A temporary folder alone does not enforce a sandbox. Real tools and mocked services can both be used within the same isolated environment.

Related guidance: Promptfoo, managing side effects and isolated workspaces.

Using them together

ConceptWhat it defines
ScenarioThe situation and expected behavior
MockHow a simulated dependency responds
SandboxThe boundary for running actions

Run a scenario using real tools, mocks, or a mixture.
Check the behavior and the result.

These concepts work together. The scenario describes the test. Mocks let us control selected dependencies. A sandbox bounds real execution. We can choose the combination needed for the behavior being tested, then use the assertion techniques discussed earlier to evaluate it. Detailed workflow setup and verification can follow once these terms are clear.
