Start with init, then review

What are skills?

Task-specific instructions with structured metadata


---
name: pre-commit-check
description: Run project checks before committing.
  Use when the user asks to commit changes
  or prepare a commit.
---

## Steps

1. Run linting: `ruff check --fix . && ruff format .`
2. Run the test suite: `pytest`
3. If either step fails, show the errors and stop
4. Stage and commit following conventional commits

What goes wrong

Skills fail silently

The silent misfire


Trigger description is too vague — agent never picks up the skill


No error. Nothing crashes. The skill just sits there.

We rewrote a SKILL.md to be "more conceptual" — it stopped triggering entirely

Action verbs matter


# Triggers ~33% of the time
description: Security review guidelines and best
  practices for code changes

# Triggers ~83% of the time
description: Run a security review on the current
  code changes. Use when the user asks to check
  security, review for vulnerabilities,
  or run a security scan.

First reads like docs — agent can answer without invoking the skill

Second describes an action the agent can't perform alone

The silent regression

Change looks fine in code review

Capability quietly stops working

...created real MRs and pushed branches

promptfoo

YAML config → assertions → CLI

Trigger test

description: 'Pre-commit check skill eval'
providers:
  - id: anthropic:claude-agent-sdk
    config:
      working_dir: ./fixtures/consumer
      setting_sources: ['project']
      skills: ['pre-commit-check']
tests:
  - vars:
      prompt: 'Run pre-commit checks before committing'
    assert:
      - type: skill-used
        value: pre-commit-check

skill-used checks actual Skill tool routing, not just output text

Three kinds of trigger prompts

tests:
  # Positive — should trigger
  - vars:
      prompt: 'Review this code for security vulnerabilities'
    assert:
      - type: skill-used
        value: security-review

  # Near-miss — should trigger sibling, not this one
  - vars:
      prompt: 'Check if the code follows our naming conventions'
    assert:
      - type: not-skill-used
        value: security-review
      - type: skill-used
        value: style-check

  # Negative — unrelated, should trigger nothing
  - vars:
      prompt: 'What time is the standup meeting?'
    assert:
      - type: not-skill-used
        value: security-review

The fixture directory pattern

fixtures/consumer/
├── .claude/skills/
│   ├── security-review → (symlink)
│   └── style-check    → (symlink)
├── .agents/skills/
│   └── ...             (same, for other agents)
└── src/
    └── app.py          (test fixture code)

Execution testing

Does the skill produce correct results?

Recall and precision


Recall

Plant a known issue

Assert the skill finds it

Precision

Present safe code

Assert the skill doesn't flag it


Precision matters more for adoption — false positives erode trust faster than missed findings

Planted diff test

# Recall — planted command injection
- vars:
    diff: file://diffs/recall-cmdinject.diff
  assert:
    - type: javascript
      value: |
        const match = output.match(/```json\s*([\s\S]*?)```/);
        const issues = match ? JSON.parse(match[1]).issues || [] : [];
        const found = issues.some(i =>
          /command.inject|shell/i.test(i.description));
        return { pass: found, score: found ? 1 : 0,
          reason: found ? 'Detected injection' : 'Missed injection' };

# Precision — safe subprocess, should not flag
- vars:
    diff: file://diffs/precision-subprocess-safe.diff
  assert:
    - type: javascript
      value: |
        const match = output.match(/```json\s*([\s\S]*?)```/);
        const issues = match ? JSON.parse(match[1]).issues || [] : [];
        return { pass: issues.length === 0, score: issues.length === 0 ? 1 : 0,
          reason: issues.length === 0 ? 'No false positive'
            : 'False positive: ' + issues[0].description };

Scenario-based testing

Test multi-step logic without side effects

Pre-written step results

Step 1 — Count commits ahead of main:
2 commits ahead of main.

Step 2 — Discover review skills:
Found skills: security-review, style-check

Step 3 — Run each review skill:
security-review: FAIL — found 1 issue: command injection
  via subprocess.run(user_input, shell=True) in src/app.py:30.
style-check: PASS — all naming conventions followed.

Step 4 — Aggregate:
1 of 2 checks failed. PR is NOT ready for review.

The LLM doesn't know it's reading pre-written results — it processes them like real output

Scenario assertions

tests:
  - vars:
      skill_content: file://../SKILL.md
      scenario: file://scenarios/security-fail.txt
    assert:
      - type: javascript
        value: |
          const lower = output.toLowerCase();
          const blocked = lower.includes('not ready') ||
                          lower.includes('status: fail');
          return { pass: blocked, score: blocked ? 1 : 0,
            reason: blocked ? 'Correctly blocked PR'
                            : 'Did not block PR' };
      - type: icontains
        value: 'security'

Test every branch: all pass, security fail, zero commits, no skills found

Taking it to CI

Catch regressions before they ship

GitHub Actions

name: Skill Evals
on:
  pull_request:
    paths:
      - 'plugins/**/SKILL.md'
      - 'plugins/**/evals/**'
jobs:
  eval:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
      - uses: promptfoo/promptfoo-action@v1
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
          config: 'plugins/dev/skills/pre-commit-check/evals/promptfooconfig.yaml'
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}

Only runs when SKILL.md or eval files change — not on every PR

Progressive rollout


  1. Start informational — report results, don't block
  2. Build confidence — team sees what tests catch
  3. Flip to blocking gate

Cost: ~$0.10–0.15 per eval run — less than debugging a broken skill
