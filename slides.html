The context problem

AI agents are only as good as the context you give them


"Improve performance, make no mistakes"

^ This rarely yields the desired outcome

The model is the same for everyone. What differs is the context we give it: project instructions, skills, and the task itself. This talk covers three things: how to write that context, how to package repeatable work as skills, and how to test that the skills actually work.

AGENTS.md

A README for coding agents — lives at your project root


  • How to install the project
  • What tools to use
  • Where the tests are
  • Key invariants and gotchas


Open spec — agents.md — read natively by most agents, including Claude Code

AGENTS.md is an open format for project instructions that coding agents read at the start of a session: how to install and test the project, which tools to use, and what to watch out for. Most agents read it natively, and Claude Code does too from v2.1.277.

One catch if someone asks: when a repository also has a CLAUDE.md, or even a personal CLAUDE.local.md, Claude Code reads that instead of AGENTS.md by default. If you need both, put @AGENTS.md in the CLAUDE.md to import it. Source: Claude Code docs, AGENTS.md.

Start with init, then review


Most agents generate a starting context file with an init command


  • Keep: what only you know — silent invariants, gotchas, non-obvious conventions
  • Remove: what the agent can already figure out — standard directory structures, obvious patterns

ETH Zurich, 2026: no significant success gain, ~20% higher cost — arXiv

The ETH Zurich and LogicStar study compared no context file, an LLM-generated file, and the developers' own file across four agent and model pairs. Success-rate differences were small and not statistically significant; the extra inference cost, about 20 percent, was. Generated repository overviews did not help agents find relevant files faster. The authors recommend limiting context files to details the agent cannot infer, such as custom build commands. Press coverage quoted minus 3 and plus 4 percent from the first version of the paper; avoid those numbers.

Use it as an index, not an encyclopedia

| Topic                | Document                     |
|----------------------|------------------------------|
| Setup & CLI usage    | `README.md`                  |
| System design        | `ARCHITECTURE.md`            |
| Interface contracts  | `specs/README.md`            |
| Coding patterns      | `docs/development/coding-patterns.md` |

  • Rule of thumb: under 150 lines (30–50 for small repos)
  • Document small invariants — things that fail silently
  • If the agent keeps making the same mistake, add a rule here

Point to deeper documents instead of copying them in. The agent can read ARCHITECTURE.md when it needs to; it should not pay for it on every turn. The line count is a rule of thumb, not a measured threshold. When the agent repeats a mistake, add a rule, and later we will see that the same mistake also deserves a test case.

What are skills?

Task-specific instructions with structured metadata


---
name: pre-commit-check
description: Run project checks before committing.
  Use when the user asks to commit changes
  or prepare a commit.
---

## Steps

1. Run linting: `ruff check --fix . && ruff format .`
2. Run the test suite: `pytest`
3. If either step fails, show the errors and stop
4. Stage and commit following conventional commits

Open spec — agentskills.io

A skill is a folder with a SKILL.md file: YAML frontmatter with a name and a description, then plain instructions. Where AGENTS.md is always on, a skill is for a specific, repeatable task. The format is an open spec, so the same skill works across agents.

What's in the context window

This is the picture to keep in mind for the rest of the talk. The top part is paid for on every turn: the system prompt, AGENTS.md, and one short entry per skill, its name and description. That is why AGENTS.md should stay short, and why the description matters so much: it is the only thing the agent sees when deciding whether to load the skill.

The bottom part is progressive disclosure. The full SKILL.md, and any references or scripts it points to, are read only when the agent picks the skill. A skill can carry a lot of detail without costing anything until it is used.

Skill folder structure

skill-name/
├── SKILL.md          # Required: metadata + instructions
├── scripts/          # Optional: executable code
├── references/       # Optional: documentation
├── assets/           # Optional: templates, resources
└── ...               # Any additional files

Extra resources are only read when the instructions reference them

Store skills in .agents/skills/ for maximum portability

Action verbs, not guide-style phrasing

Skills load in two ways: explicitly, when the user types the slash command, or automatically, when the agent matches the request to a description. Automatic loading is where things go wrong. If the description reads like documentation, the agent decides it already knows the topic and answers by itself. Nothing errors; the skill simply never runs. Describe an action and when to use it.

Instructions, not documentation


❌ Documentation

## Security Review

Security reviews check
for common vulnerabilities
like injection, XSS, and
hardcoded secrets.

✅ Instructions

## Steps

1. Read the staged diff
2. Check for injection,
   XSS, hardcoded secrets
3. Output JSON with issues
4. If clean, say "No issues"

The agent doesn't need to understand the concept — it needs to know what to do

The same applies to the body. The model already knows what a security review is. What it does not know is your process: which diff to read, what to check, what format to return, and when to stop. Write steps. Copying reference documentation in adds tokens without adding capability.

Testing skills

Skills fail silently


  • Silent misfire — description too vague, agent never picks it up
  • Silent regression — someone "improves" the instructions, skill breaks
  • Side-effect surprise — eval run creates real MRs, pushes branches

Unlike code, there's no exception — you find out from your users

Skills fail in three quiet ways. A vague description means the skill never loads, and the agent improvises instead. A well-meant edit to the instructions passes code review and quietly breaks the behavior. And a test run of a skill that takes actions can take those actions for real: we had an eval run create real merge requests and push branches. None of these raise an error, so the only way to notice is to test.

Layers of skill evaluation

This is the map for the rest of the talk. Work from the bottom up. Static checks need no model: is the frontmatter valid, is the skill within its token budget, does its description overlap with a sibling's. Trigger tests ask whether the agent loads the skill when it should and leaves it alone when it should not. Execution tests ask whether the skill does the job correctly once loaded. At the top, compare the same tasks with and without the skill: does it make the agent better at all?

Each layer up is more realistic, slower, and more expensive, so run the lower layers often and the upper ones when something changes.

Trigger test

description: 'Pre-commit check skill eval'
providers:
  - id: anthropic:claude-agent-sdk
    config:
      working_dir: ./fixtures/consumer
      setting_sources: ['project']
      skills: ['pre-commit-check']
tests:
  - vars:
      prompt: 'Run pre-commit checks before committing'
    assert:
      - type: skill-used
        value: pre-commit-check

skill-used checks actual Skill tool routing, not just output text

The provider runs the Claude agent in a small fixture project that has the skill installed. The test sends a natural request and asserts that the agent actually invoked the skill. That check looks at the tool call, not at whether the answer happens to mention pre-commit.

Three kinds of trigger prompts

tests:
  # Positive — should trigger
  - vars: { prompt: 'Review this code for security vulnerabilities' }
    assert:
      - { type: skill-used, value: security-review }

  # Near-miss — should trigger sibling, not this one
  - vars: { prompt: 'Check if the code follows our naming conventions' }
    assert:
      - { type: not-skill-used, value: security-review }
      - { type: skill-used, value: style-check }

  # Negative — unrelated, should trigger nothing
  - vars: { prompt: 'What time is the standup meeting?' }
    assert:
      - { type: not-skill-used, value: security-review }

One positive test is not enough. Near-misses matter most once you have more than a handful of skills: a broad description can capture requests meant for a sibling. Here a naming-convention question must go to style-check, not security-review. Negative tests confirm the skill stays out of unrelated work. The fixture project matters too: skills must be installed where the agent discovers them, or the agent may read SKILL.md as a plain file and the test passes for the wrong reason.

Execution testing

Does the agent carry out the task correctly?


Give it a defined situation.
Observe its behavior and check the result.

Trigger testing asks whether the agent selects a skill. Execution testing asks what happens when it uses the skill. The result might be an answer, a generated artifact, or a change in an external system. We first need a few concepts for setting up these tests.

Source: Anthropic, task definitions and outcomes in agent evals.

Scenarios

A repeatable situation we want to test


  • A task and the information available at the start
  • Conditions the agent encounters
  • Expected behavior or an acceptable result

Example: required information is missing. Should the agent ask for it?

A scenario is a test case: a task, its context, and criteria for success. We can create scenarios for a normal request, incomplete input, or a dependency failure. Repeating a scenario helps us compare behavior. The expected result belongs to the evaluation; giving the agent the answer would weaken the test.

Mocks

Controlled replacements for tools or services


  • Return a chosen response when the agent makes a call
  • Make success and failure conditions repeatable
  • Record calls so we can check how a dependency was used

Example: an API returns a timeout. How does the agent respond?

A test double stands in for a real dependency. A stub supplies a response; a mock can also check interactions. Here we use mocks as the broad introductory term for controlled tool or service replacements. The agent still chooses whether and how to call the tool. These tests tell us about its response to the simulated behavior; testing the real integration is a separate step.

Sandboxes

Isolated environments for running actions


  • Allow real tools to operate on test data
  • Enforce limits on what execution can access or change
  • Start each run from a known state

Example: create and edit files inside a disposable test environment.

The sandbox provides an execution boundary. Its configuration determines file, process, and network access. Resetting test state supports repeatability; isolation controls side effects. A temporary folder alone does not enforce a sandbox. Real tools and mocked services can both be used within the same isolated environment.

Related guidance: Promptfoo, managing side effects and isolated workspaces.

Using them together

ConceptWhat it defines
ScenarioThe situation and expected behavior

Run a scenario using real tools, mocks, or a mixture.
Check the behavior and the result.

These concepts work together. The scenario describes the test. Mocks let us control selected dependencies. A sandbox bounds real execution. We can choose the combination needed for the behavior being tested, then use the assertion techniques discussed earlier to evaluate it. Detailed workflow setup and verification can follow once these terms are clear.

Choosing a grader

Use the cheapest grader that can express the rule.

Combine several checks on one run — schema, code, and a rubric.

Once we have an output, something must decide whether it passes. Promptfoo supports the whole range. On the left, exact and regex matches and JSON schemas are deterministic, free, and repeatable: use them for a status value, a required heading, or the shape of the output. Code assertions handle exact fields, counts, and relationships, for example that a required label is present.

On the right, an LLM rubric judges meaning when correct wording can vary, such as whether a report preserved the user's facts. An agent judge goes further and uses tools to inspect files and state. These are flexible but cost tokens, can vary between runs, and need calibrating against outputs a human has labeled good or bad. A schema pass can hide a wrong value, so one run usually gets several checks.

Source: Promptfoo assertion types.

Exact checks

AssertionUseful for
equalsAn exact status or classification
contains / not-containsRequired or forbidden literal text
regex / not-regexA heading or other text pattern
 
# Check a heading, allowing the words elsewhere in the report
assert:
  - type: not-regex
    value: '(^|\n)### \*\*Root Cause\*\*(\r?\n|$)'

Make the check as precise as the rule it protects.

A skipped optional section gives us a concrete example. Forbidding the words Root Cause everywhere would also reject a valid note explaining what was skipped. This expression checks the actual Markdown heading. Exact checks are repeatable and require no judge-model call; choosing the right condition still takes judgment.

is-json: whole output. contains-json: JSON within other text.

The schema checks required fields and their types. It intentionally accepts any string in labels, so the wrong label can pass. A schema can also enforce an enum or const; the next slide uses code to show how domain rules can be expressed separately. A provider's structured-output setting constrains generation, while this assertion checks the returned result.

JavaScript assertions

assert:
  - type: javascript
    value: |
      try {
        const report = typeof output === 'string'
          ? JSON.parse(output) : output;
        const pass = Array.isArray(report?.labels) &&
          report.labels.includes('ai-generated-jira');
        return { pass, score: pass ? 1 : 0,
          reason: pass ? 'Required label present'
                       : 'Required label missing' };
      } catch {
        return { pass: false, score: 0, reason: 'Invalid JSON' };
      }

Use code for exact fields, counts, and relationships.

Python assertions are also supported. Larger graders can live in file:// scripts.

The wrong label from the previous slide now fails. Parsing errors fail too, instead of becoming an empty result that accidentally passes. Returning a reason makes a failed assertion easier to investigate. Code can enforce a known contract, but this check alone says nothing about whether the report preserves the user's facts.

LLM as a judge

# Assertion excerpt; source_facts is a test variable
assert:
  - type: llm-rubric
    provider: openai:gpt-5-mini
    value: |
      Source facts: {{source_facts}}
      Pass only if the report preserves the supplied
      reproduction steps, observed result, and environment.
      Fail if it invents a root cause or a proposed fix.
      Cite the relevant output text in your reason.

Useful when correct wording can vary.

Calibrate the rubric against human-labeled good and bad outputs.

The grading model is configured separately from the system under test.

The judge compares the report with source facts supplied through the rubric. This lets it evaluate meaning when several phrasings would be acceptable. Define concrete pass and fail conditions, inspect its evidence, and check agreement with human judgments. Pin the judge configuration for comparisons. Model grading adds cost and can vary, so retain exact code checks for exact rules.

Agent as a judge

assert:
  - type: agent-rubric
    provider:
      id: anthropic:claude-agent-sdk
      config:
        working_dir: ./fixtures/report-output
    value: |
      Read source-facts.md and outputs/preview.md.
      Verify that the preview preserves the source facts.
      Fail on invented reproduction steps or environment.
      Cite file evidence for the verdict.

The judge gathers evidence from files using tools.

Give it the matching run's artifacts and read-only access.

Earlier the agent was the thing we tested; here the agent is the one doing the grading. The target could be another agent, a model, or an application. Unlike the preceding text-only rubric, this grader needs tools and a workspace containing the evidence. The fixture path is illustrative: stage source-facts.md and the generated preview there for the run being graded. Promptfoo's Claude agent provider defaults to read-only tools. Use code for checks that are already exact and reserve this judge for artifact inspection requiring interpretation.

Each row answers a different question. A schema pass can coexist with a factual error, and skill invocation can coexist with an incorrect outcome: skill-used tells you the skill was picked. It doesn't tell you the result was right; for that you need one of the other checks. Use independent reference facts and known outputs to validate the graders themselves. With vs without the skill

Re-run after every model upgrade — newer models outgrow skills.

This is the top of the pyramid and the question most teams skip: does the skill help at all? Run the same tasks, in the same fixture, with fresh state each time, once without the skill and once with it. Repeat each a few times, because agent runs vary. Compare pass rate, and also tokens and time: a skill that gets the same result faster is still worth having.

If there is no gain in either success or cost, the skill is only adding context to every session; delete it. Re-run this after model upgrades. A newer model may already do what the skill teaches, and deleting a skill it has outgrown is a good result. A cheap first check: if with and without score the same, confirm the skill actually loaded before rewriting it.

Sources: agentskills.io, evaluating skills, Google Cloud, evaluate agent skills before they bloat your context window.

Run it more than once

One run is an anecdote. Compare pass rates.

Repeats multiply the cost

3 cases × 2 configs × 3 repeats = 18 agent runs, plus judge calls

npx promptfoo eval --repeat 3 --no-cache

Cheap checks on every change. Expensive ones when it matters.

Agents don't give the same answer twice. The model picks its words with some randomness, and an agent makes many decisions in a row, so small differences add up. Google's team found that more than a third of their benchmark tasks scored differently when they re-ran identical code and prompts. So one pass or one fail tells you very little. Run each case several times and compare pass rates: two out of five against four out of five is a real difference; one pass against one fail is not.

Repeats cost money. Every case runs once per configuration and once per repeat, plus any judge calls. Our small with and without example has three cases and two configurations; three repeats makes eighteen agent runs. Three repeats is a smoke check; more repeats give more confidence and cost more. Use --no-cache when measuring, otherwise Promptfoo can reuse earlier answers. The viewer shows tokens, cost, and latency where the provider reports them.

To keep the bill down, go back to the pyramid: exact and code checks before judges, a cheaper model as the judge, and the expensive suites only when a skill or model changes. Source: Google Cloud, evaluate agent skills before they bloat your context window.

Can a cheaper model do it?

A skill can pay for itself by letting a cheaper model do the job.

An example outcome, not a measured result. Run your own cases to find out.

With and without asks whether the skill helps. Add a second model and you can ask a money question: does the skill let a smaller, cheaper model do the job?

Read the grid by rows. If the strong model passes either way, the skill adds nothing for that model; that's the "delete it" case we saw. If the cheaper model fails without the skill but passes with it, the skill is worth real money: you can switch models for that task. There's a third outcome too: the cheaper model fails even with the skill. Then the skill depends on a strong model. Simplify the steps, or move the hard parts into scripts, and test again.

This matters most if you want to run agents on smaller or self-hosted models. The grid shows possible outcomes, not results we measured; the next slide shows how to set up the comparison.

The latest stored report-bug baseline in this checkout passes all 51 assertions across five cases: complete input, skipped optional sections, missing configuration, programmatic input, and adversarial input. That is useful coverage, but the number has a specific denominator: assertions in selected cases.

Most checks inspect structure or proposed metadata. They do not comprehensively verify preservation of source facts. Files describing Jira calls do not demonstrate a successful real API interaction. Progressive rollout


  1. Start informational — report results, don't block
  2. Build confidence — team sees what tests catch
  3. Flip to blocking gate

Re-run the suite when you change models, not only when skills change

Track run cost and judge cost alongside pass rates.

Start here


  1. Pick one skill in your project
  2. Add trigger tests — positive, near-miss, negative
  3. Run them with and without the skill
  4. Add them to CI as informational

Step 2 takes 15 minutes. It will tell you more than rereading the SKILL.md.

If you take one thing away: pick a skill you already rely on and give it a trigger test today, one positive, one near-miss, one negative. Then run the same tasks with and without the skill to see whether it earns its place. Put it in CI as a report first. The companion repository has working versions of every step.
